## 项目成果

本项目实现了一套面向企业内部申请与审批的 B/S 系统。员工可提交采购、差旅、报销和自定义表单申请；审批人按流程待办处理申请；管理员维护组织、账号、数据授权、流程模板和系统配置。系统提供站内通知、SSE 更新、邮件投递、统计查询，以及 Web 和 uni-app 移动端（H5、微信小程序构建目标）。

后端使用 Java 17、Spring Boot、Spring Security、MyBatis-Plus 和 Flyway；PostgreSQL 保存组织权限、申请、流程实例、审批任务和日志；MinIO 保存私有附件。Web 前端采用 Vue 3、TypeScript 和 Element Plus，移动端采用 uni-app。仓库提供 Docker Compose 与 Nginx 部署配置。

核心实现包括：

- 角色功能权限、数据范围和具体待办审批权分开判定；服务端校验资源访问与审批人身份，禁止自审，系统管理员默认不能审批或查看业务正文。
- 模板按版本发布。申请提交时保存模板版本、条件计算和审批人解析快照；流程支持条件节点、单签、会签和或签，以及撤回、驳回、转办和催办。
- 对申请金额在服务端按分计算或重算，对上传文件检查真实类型、扩展名与 PDF 主动内容，并由后端鉴权后读取私有对象存储。
- 使用 PostgreSQL 条件更新、唯一约束和事务控制审批状态；关键写操作支持幂等键与成功响应重放，日志和通知随业务事务写入。

## 设计取舍

PostgreSQL 的 JSONB、部分唯一索引和触发器适合保存流程快照、约束唯一待办并保护只追加日志；MyBatis-Plus 便于显式表达带状态与版本条件的更新。附件放在 MinIO 而不是数据库中，浏览器不直接取得对象存储地址，下载需经后端权限检查。

提交时预先解析并快照整条审批路径，可以让已提交申请不受后续模板或组织配置变化影响；相应地，审批人离职或停用时，需要管理员通过转办处理旧待办。跨报销单的相似票据只作提示，不自动拒绝，以保留合法分次报销等情形的人工判断空间。

## 验证状态与交付边界

[测试报告](test_report.md)记录了后端、Web 与移动端自动化测试结果，以及前端静态检查和构建结果；测试数量与逐项结果以该报告为准。集成测试使用真实 PostgreSQL 测试流程和数据库约束，但文件存储由 mock 替代。

真实 PostgreSQL 全套回归已通过；Web 用章申请已在真实后端上完成申请人提交、部门负责人批准、印章管理员批准及申请人查看结果的浏览器验收。[验收录像与操作说明](demo_video.md)已保存。移动 H5 也验证了登录、完成通知、申请详情与统计图表。Docker Compose 部署已验收：`docker compose up -d --build` 后 5 个常驻服务正常运行（postgres、minio、backend 健康检查通过），minio-init 初始化后成功退出；经 nginx 验证了 Web / H5 页面、登录与 Cookie 续期、附件上传下载（MinIO）、SSE 推送和 Mailpit 收信；数据库运行账号没有建表和修改日志表的权限，MinIO 专用 key 只能访问 `eas-files` 桶；正式部署（profile 留空并设置 `EAS_ADMIN_PASSWORD`）只创建引导管理员、不加载演示账号；前面再加一层 HTTPS 反向代理时同源请求正常、跨域请求仍被拒绝。真实微信设备尚未验收。
