## 1. 实验题目与目标

### 1.1 实验题目

企业审批系统的设计与实现。

### 1.2 实验目标

本实验围绕企业内部申请、审批和管理需求，完成一套包含 Web 与移动端的 B/S 应用。目标包括：梳理采购、差旅、报销和可配置表单的业务流程；设计组织、权限、流程及业务数据模型；实现有权限边界、状态约束和并发保护的审批服务；提供可运行的前后端、数据库迁移和部署配置；通过自动化测试检查主要业务规则与异常场景。

## 2. 系统范围与功能

系统支持员工注册、管理员审核、登录和账号维护。员工可保存草稿、提交申请、查看处理进度、撤回进行中的申请，并将被驳回或撤回的申请复制为新草稿。

业务类型包括：

- **采购：** 采购明细与金额重算、供应商报价比较、拟选供应商和单一来源说明；报价和金额规则由服务端校验。
- **差旅：** 行程、起止时间、预算和同行人信息；系统计算自然日天数，并按预算或天数条件决定是否进入企业负责人节点。
- **报销：** 费用明细与票据、无票原因，以及与本人已通过采购或差旅申请的关联；同一报销单的票据重复会被拦截，跨单疑似重复会提示财务复核。
- **自定义申请：** 管理员设计表单字段和审批节点。初始化数据包含请假、用章模板；模板通过草稿、校验和发布版本管理。

审批人处理分配给自己的待办。系统还提供部门、财务和企业统计，站内通知、SSE 推送、邮件投递、待办催办与超时提醒，以及用户、部门、角色、授权、模板、费用类型、系统配置、转办和审计等管理功能。

## 3. 总体架构与技术实现

系统由后端 API、Web 前端、移动端、关系数据库、对象存储和反向代理组成。接口统一使用 `/api` 前缀。后端以 Controller 接收和校验请求，Service 承载业务事务，Mapper 负责显式 SQL 与数据访问；`flow` 包实现审批路径解析和状态流转，`notify` 包处理通知，`job` 包负责定时清理和超时提醒。

| 层次 | 实现 |
|---|---|
| 后端 | Java 17、Spring Boot 3.3、Spring Security 6、JWT、MyBatis-Plus、Flyway |
| 数据库 | PostgreSQL 16；迁移脚本创建结构、约束和基础数据 |
| 文件 | 私有 MinIO 桶；服务端检测、绑定和鉴权后转发下载 |
| Web | Vue 3、TypeScript、Vite、Element Plus、Pinia、Vue Router、ECharts、axios |
| 移动端 | uni-app（Vue 3、TypeScript），构建目标为 H5 与微信小程序 |
| 部署 | Docker Compose 编排，Nginx 托管 Web/H5 并反向代理 API，Mailpit 用于演示邮件 |

Web 与移动端共用接口类型和金额工具，但各自实现页面。H5 和微信小程序使用适合窄屏的卡片、分步表单和移动端输入控件。

## 4. 数据库设计

数据模型按组织与权限、模板与流程、业务明细与附件划分。主要实体包括部门和用户、角色与权限点、数据范围授权、流程模板及其版本、申请及业务明细、流程实例与节点、审批任务、审批日志、附件、通知、审计和幂等记录。

金额以整数分保存，避免浮点累计误差；时间字段带时区。模板表单、节点配置和提交时流程快照使用 JSONB。枚举值以字符串及检查约束维护。Flyway 负责版本化迁移，避免以手工改库作为部署步骤。

数据库约束参与业务正确性：包括用户名和邮箱不区分大小写的唯一性、同一报销单票据去重、同一流程实例只存在一个活动节点、同一节点同一审批人避免重复待办，以及通知和幂等记录去重。审批日志、管理审计和审批人变更记录采用只追加约束；草稿允许软删除，已提交流程及其记录保留。

## 5. 权限与安全

权限分为三个维度：

1. **功能权限：** 由角色及权限点控制接口能力，角色包括员工、部门负责人、财务审批人、企业负责人和系统管理员。
2. **数据范围：** 用户可查看本人申请、与自己相关的审批申请、本人负责部门范围内的申请，或管理员显式授予的部门/全部范围。详情、附件和列表均由服务端执行授权判断。
3. **审批权：** 只由当前流程节点上分配给该用户的待办决定，不因持有某审批角色而自动获得所有申请的审批权。

管理员角色不含审批权限，默认也不能读业务正文；若获授业务内容读取权限，访问会写入审计日志。系统拒绝自审。无资源查看权时返回资源不存在类结果，减少对申请是否存在的泄露。申请人、所属部门、流程状态和合计金额由服务端确定或重算，不接受客户端覆盖。

认证使用 BCrypt 保存密码哈希，访问令牌采用 JWT，刷新令牌轮换并在数据库保存哈希；用户停用、密码或权限变更可使旧令牌失效。上传文件按内容识别 JPEG、PNG、PDF，扩展名需匹配，PDF 会检查主动内容；对象存储桶不公开，下载前由后端检查附件权限。

## 6. 审批流程、并发与幂等

模板发布时校验表单字段、节点和审批人规则。申请提交时，服务端校验业务数据、重算金额、计算节点条件、解析审批人，并将所用模板版本及审批路径保存为流程快照。只激活首个有效节点；该节点完成后再创建下一节点的待办。单签、会签与或签均受支持。会签要求所有人同意后推进，或签由任一审批人的处理决定节点结果，其他待办随之取消。

流程写操作在数据库事务中完成。申请状态更新使用状态、版本和当前节点作为条件，只有更新行数符合预期才继续；随后处理待办、更新节点并写审批日志和通知。申请行和任务的更新顺序保持一致，配合 PostgreSQL 行锁与唯一约束，避免撤回和审批并发造成重复流转。失败操作整体回滚，并以冲突响应提示客户端刷新。

提交、批准、驳回、撤回等请求使用 `Idempotency-Key`。服务端对用户、键、端点和请求内容建立指纹，在事务级互斥后保存成功响应；相同键和内容可重放原响应，不同内容复用同一键会冲突。数据库版本条件、审批日志唯一约束、待办约束及通知去重为并发重试提供额外保护。

流程路径在提交时解析并固化，模板后续发布不会改写已提交申请。此选择提高了审批历史的可解释性，但审批人离职或停用时需管理员填写原因转办。被驳回或撤回的流程作为终态保留，申请人通过复制生成新的申请，不覆盖原审批历史。

## 7. 业务实现要点

业务服务将通用申请和采购、差旅、报销、自定义表单的校验分开实现。金额以分传递并由服务端计算；差旅时长、预算条件、采购报价、报销明细、票据和关联申请在提交时再次校验。自定义表单按当前模板 Schema 渲染和校验，未定义字段不接受；已发布模板版本不可直接修改。

附件先作为临时对象上传，再在草稿保存时绑定到申请。服务端校验上传人、文件类型、大小、哈希和引用归属，下载时通过统一资源权限策略。MinIO 对象写入不属于数据库事务，若后续数据库事务回滚，服务会清理本次新写入的对象。

业务事务写入站内通知记录，提交后由 SSE 推送；邮件投递单独记录状态并按策略重试，邮件不包含金额明细和票据内容。管理操作写审计日志，业务审批写只追加审批日志。统计按提交时部门和提交时间归属；通过率以已通过和已驳回申请为分母。

## 9. 部署方式

仓库提供 `template.env`，部署时复制为 `.env` 并填写数据库密码、MinIO 凭据和 JWT 密钥，然后在项目根目录构建并启动 Compose 服务：

```bash
cp template.env .env
docker compose up -d --build
```

Compose 配置包括 PostgreSQL、MinIO 初始化、Mailpit、后端和 Nginx。数据库由 `eas_owner` 执行 Flyway 迁移，应用以仅具备日常数据操作权限的 `eas_app` 连接；MinIO 使用仅访问应用私有桶的专用凭据。Nginx 对外提供 Web 根路径和移动 H5 `/m/`，并将 `/api/` 转发至后端；Mailpit 演示收件箱使用 8025 端口。演示配置可载入演示账号、模板和示例申请。

以上为仓库提供的部署方案，不代表 Docker 环境已完成验收。数据卷初始化脚本只在 PostgreSQL 数据卷首次建立时运行，重置或修改初始化凭据时需按部署文档处理现有卷。
